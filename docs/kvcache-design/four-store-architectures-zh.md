# 四个场景的 Store 架构草案

Prefill 跨实例共享已发布的对象。Decode 由请求所属 Client 管历史块映射。训练由 rank 所属 Client 管激活句柄。Engram 由加载器发布只读权重，推理 Client 按绑定版本取行。这四个所有权选择分别决定了谁能分配空间、谁能发布可读状态，以及读路径是否需要访问独立元数据服务。[原始需求与源码依据](./prefill-kvcache-store-requirements-zh.md) · [领域术语](../../GLOSSARY.md)

## 组件与完成条件

**Client** 接受业务读写请求，解析逻辑标识并提交传输。**Server** 提供存储容量、授权访问区间并负责安全回收。**Transport** 在已指定的源和目的区间间传输数据并报告完成。**空间管理**决定哪些物理区间可分配，**元数据管理**记录逻辑标识对应的位置和状态。**Master** 指独立部署的元数据服务。下列部署都是设计提案。

| 维度 | Prefill | Decode DSA | 训练 OpReplay | Engram |
| --- | --- | --- | --- | --- |
| Client 执行位置（稳态） | 计算节点 Host CPU | 计算节点 NPU | 计算节点 Host CPU | 计算节点 NPU |
| Server 部署位置 | 远端内存节点、远端 SSD 节点 | 远端内存节点 | 远端内存节点 | 远端内存节点 |
| 空间管理职责归属 | Master 选层级和节点，Server 分配对象区间 | Server 授段，Client 按请求分配块 | Server 授段，Client 按张量载荷分配变长区间 | Server 按表分片分配连续区间 |
| 元数据管理职责归属 | 独立 Master 持有共享 key 目录，Client 持有读写会话 | Client 持有请求块表和可读历史边界；DSA 自管热槽驻留表 | Client 持有 rank 私有句柄表；OpReplay 自管算子调用记录 | 加载器发布版本目录，Client 持有绑定版本的表描述符 |
| 稳态查询所需元数据的驻留位置 | 目录在 Master 的 Host DDR，会话在 Client 的 Host DDR | 请求块表、各层布局和可读历史边界在 HBM | 句柄表在计算节点 Host DDR | 表描述符在 HBM |
| Transport 提交位置 | 计算节点 Host CPU；读盘由 SSD 节点 CPU 提交 | 计算节点 NPU | 计算节点 Host CPU | 计算节点 NPU |

远端 DDR 的 Transport 端点在计算节点与内存节点。Server 在控制面注册内存、授权访问；授权有效时，网卡可直接处理数据访问。**提交位置、源地址、目的地址是三个独立属性**。训练由 Host 提交也可以走 RH2D。Decode、Engram 要求设备侧提交并观察完成，这属于待验证的硬件前提。

一次写入有两个可观察时点：Transport 读完源区间后，调用方可在其他使用者也结束后覆盖源；Store 满足相应场景的发布条件后，读者才可依赖远端副本。一次读取也有两个时点：目标 HBM 可见后可以开始消费；最后一个消费者结束后才能覆盖该目标。实现可以用同一事件满足多个条件，但接口要说明它保证哪些条件。

## Prefill：共享 key 的发布与跨实例读取

- **业务与接口。** vLLM 提供 key 和 HBM 区间。block-wise 读写整对象；layer-wise 额外指定对象内 range。同一 key 覆盖同一 token 块的各兼容层。以 BF16、128-token 块为例，单层 CKV 为 128 KiB 区间，KPE 为另一个 16 KiB 区间。
- **通信与数据。** Worker 在进程内调用 Client。Client 用批量 RPC 向 Master 预留、发布或打开读会话。Master 协调 Server 分配空间，读会话固定所用位置。DDR 命中走 RH2D；SSD 命中由 SSD Server 经 NVMe 读入注册缓冲，再传至 HBM。写入按相反方向搬运。逐层复用会话中的位置。
- **边界案例。** A 写完第 1 层并收到源区间释放事件，B 此时查询相同 key。A 可以按计算依赖复用该层 HBM；直到所有约定层和分量写齐并提交，B 才能命中。若其他写者已发布完整副本，B 可以读取那个副本。回收已发布区间前须等待引用它的读会话和在途传输结束。
- **验证指标。** 分 DDR/SSD 命中测量从 key 查询开始到首个所需层 HBM 就绪的 P99，并记录后续各层等待数据的时间。

## Decode DSA：请求私有的远端块与设备侧召回

- **业务与接口。** DSA 决定 Top‑K、命中、逐出和 HBM 目标热槽。写入时提供请求、层、逻辑块号和尾块源区间；读取时提供请求、层、去重后的 miss token 位置和配对的 HBM 目标区间。Store 管远端空间、寻址与复制。
- **写与发布。** Host 通过控制 RPC 提前向 Server 取得远端 DDR 段及访问凭据。NPU Client 在授权段内为请求的逻辑块领取物理块号，同一组各层复用该映射，按层将完整块从 HBM 写到远端 DDR。当前连续块的约定层和分量全部成功写入后，Client 推进可读历史边界。预留耗尽时等待补充或报告容量不足，保持已发布范围有效。
- **读与通信。** DSA 通过设备侧接口将位置和目标区间传给 Client。Client 校验可读范围，用请求块表、层基址和块内偏移计算远端地址，向设备可提交的队列批量提交 RH2D。目标 HBM 可见后报告完成。段内分配、读时查询和传输完成判断均在 NPU 内闭环。独立 Master 和逐 miss RPC 均不参与稳态路径。
- **粒度与边界案例。** 一个请求当前 step、当前层有 M 个实际 miss。656 B 打包行是 M 个离散源地址、每址 656 B；512 B 和 64 B 紧邻且无额外字段时，是 M 个离散源地址、每址 576 B。若这两个分量分存，则各有 M 个离散源地址，分别每址读 512 B 和 64 B。当前 vLLM-Ascend 的 BF16 分存示例则是 M 个 CKV 地址各读 1024 B，另 M 个 KPE 地址各读 128 B。M 为零时无需 RH2D。DSA 即使更换热槽逐出策略，只要仍给出有效目标区间，Store 的读接口就保持成立。
- **回收与指标。** 请求结束后，Client 等在途读写结束再复用其远端块；DSA 单独保证热槽消费结束。按 M 和行布局测量从 DSA 交付 miss 列表到全部目标行 HBM 可见的 P99。

## 训练 OpReplay：句柄的生命周期长于一次传输

- **业务与接口。** OpReplay 管“哪次算子调用要保存、何时重放、何时消费”。Client 登记源张量并返回激活句柄，维护驻留位置、载荷布局及完成状态。OpReplay 指定消费顺序或预取时点，Client 按该约束及 HBM 预算安排换出和预取。
- **空间与通信。** Rank 进程内调用 Client。Client 通过控制 RPC 向 Server 批量取得远端段，实际换出时才按载荷分配区间。写出为 HBM → 远端 DDR，预取为 RH2D，均由 Host 提交。一个连续 BF16 张量 `[1, 4096, 4096]` 的单向载荷是 32 MiB。句柄只有该 rank 使用，稳态查询由 Client 完成。
- **边界案例。** 前向刚取得句柄，激活可能仍只在 HBM。此时触发重放可直接使用有效副本；若写出正在进行，Client 保持源的生命周期。若反向提前结束，逻辑句柄可以作废，但正在被 RH2D 读取的远端区间要等传输结束再归还。源 HBM 的最后有效副本还承担恢复责任时，释放前须确保已有可恢复副本。
- **验证指标。** 按载荷大小记录换出到源 HBM 可释放的时间，以及从重放算子具备其他执行条件到激活就绪所额外等待的时间。两项分开衡量前向容量压力和反向停顿。

## Engram：版本绑定后按行读取只读分片

- **业务与接口。** 模型从 token 上下文计算哈希行号。Client 接收绑定的表版本、层、行号列表和配对的 HBM 输出区间。表目录给出行号范围、远端分片基址和行宽，Client 用分片内行号计算地址。模型持有各 head 与输出位置的对应关系。
- **空间与通信。** 加载器在计算节点 Host 通过 RPC 请求 Server 分配分片，数据上传完成后发布完整版本目录。推理实例绑定版本时取得描述符并装入 HBM。NPU Client 按远端分片批量提交 RH2D。若模型采用 TP，各 rank 读取分给自己的行，汇合各 rank 结果的集合通信由模型执行。
- **粒度与边界案例。** DS‑V4.1‑Flash 每个有效文本 token、每个 Engram 层对应 **24 个离散源地址，每址读 264 B**，覆盖全部哈希 head。若查询在途时发布新版本，它仍从已绑定的旧版本取齐各行；待旧绑定和在途读取全部释放后才能回收旧分片。推理期间无需逐行分配、更新或访问中心目录。
- **验证指标。** 行号一经确定即可提交各层读取。分别测量各 Engram 层从门控具备其他执行条件到本批行就绪所额外等待的时间，首个 Engram 层单列。

## 首个待定问题

**远端 Transport 能否在目标 NPU 上由设备提交整批离散 RH2D，并在同一设备上向消费算子报告目标 HBM 可见？** 这是 Decode、Engram 能否采用上述部署的共同前提。验证时，Decode 保留每层实际 miss 列表和等待窗口，Engram 保留每层 24 个离散地址及其可提前提交的时间。训练的大张量带宽测试无法回答这个问题。当前文档给出拟议架构及验证口径，远端时延尚待实测。
